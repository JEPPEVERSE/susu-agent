# susuAgent v0.2 architecture

v0.2 将运行过程划分为三个不同频率的阶段：

1. 每道题预计算一次：`subject route -> solution_agent -> SolveOutcome gate -> solution_verifier -> teaching_planner`。
2. 每轮对话执行一次：`teaching_executor` 返回学生回复、状态增量和学习证据，代码负责校验与合并。
3. 完成节点低频执行：`student_model_summarizer` 返回 `StudentModelPatch`，长期模型仓库使用乐观锁合并。

持久化的题目状态使用 schema version 6，包含题目状态、`solution`、`verification_report`、`teaching_strategy`、`learning_evidence` 和执行游标。旧版状态会自动迁移。

`StudentModel` 和 `TeacherModel` 是跨会话长期模型。`TeachingState` 是题目级短期状态。`personal_ai` 当前只预留 principal、consent、data classification 和 encryption reference，不存放密钥。

求解与验证之间最多按 `MAX_SOLUTION_REVISIONS` 循环；教学执行层只能沿策略图推进，遇到未覆盖情形返回 `replan_required`。普通轮次的主路径保持为一次模型调用。

## 题目路由与求解状态

`subject` 由应用配置和已注册的 lesson plan 在任何 Agent 运行前确定，并保存在 `TeachingState.lesson_plan.subject`；Solution 不再重复输出 subject。当前只有 `math` 教案，配置未知学科时会在代码层直接拒绝启动编排。

Solution Agent 返回受代码校验的 `SolveOutcome`：

- `solved` 必须携带完整 Solution，随后才允许进入 verifier。
- `incomplete` 和 `ambiguous` 必须携带澄清问题，不能携带伪造解法。
- `unsupported` 不进入 verifier。

题目状态、澄清问题和学生补充信息保存在 `original_problem`，不再混入 Solution。

## Solution v2

Solution 只描述已解决题目的结构化解法。保留 `goal`、`known_conditions` 和 `assumptions`，删除重复的 `subject`、`problem_statement`、`problem_status`、`clarification_questions`、顶层 `knowledge_points` 和 `likely_student_difficulties`。

SolutionStep 使用稳定的 snake_case `concept_ids`。概念 ID 不参与 verifier 判断，只供 TeachingPlanner、TeachingExecutor 的 LearningEvidence 和结束时的 StudentModel summarizer 对齐。学生困难预测由 TeachingPlanner 的 `anticipated_difficulties` 统一负责。

## Verifier 边界与上下文

Verifier 只检查最终答案及可达性、SolutionStep 的显式数学推导、步骤与 lesson plan 的对应关系。它不评价 TutorQuestion、提示阶梯、知识点、学生困难、话术和迁移活动。

验证失败后的重试会同时携带上一版 Solution 和 VerificationReport，在原解答上定向修订，并重新核算受影响步骤及其下游依赖；不会只拿错误报告从头盲目生成。一次性结构化 Agent 若仅发生 JSON 或 Schema 错误，可进行有限次数的格式修复；语义验证重试与格式修复分别计数。

从 TeachingState v5 升级到 v6 时保留可迁移的 Solution，但主动失效旧 VerificationReport 与 TeachingStrategy；下一次进入该会话时按新 verifier/planner 契约重新生成，防止旧 `passed` 缓存绕过新验证。

Verifier 上下文是专用投影：`origin_problem + solution correctness projection + referenced lesson_plan sections`。TutorQuestion、concept_ids、StudentModel、TeacherModel 和完整 TeachingState 均不会进入 verifier；重复的教案章节会在代码层去重。

## 教学轮次一致性契约

`teaching_executor` 的输出在写入数据库前依次经过 Pydantic、当前状态和策略图三层校验：

- 继续教学时必须登记且只登记一个 `open_question`，并在学生可见回复中逐字出现。
- 表达 Agent 可依据目标策略节点的 `prompt_intent`、绑定的 Solution 问题和提示阶梯自然组织提问，但不能跨节点引入新的解题路线。
- 有开放问题时必须先记录学生回答、判断与依据；没有开放问题时禁止伪造回答归属。
- 策略节点、Solution 步骤、Solution 问题和 lesson plan 步骤的游标由代码同步，不能各自漂移。
- 状态中最多存在一个开放问题，`teaching_progress.open_question` 必须与问题历史一致。
- 验证通过必须覆盖全部 Solution 步骤；教学策略中的问题必须属于其声明的 Solution 步骤。

执行输出不满足契约时不会展示给学生或写入状态。系统默认通过 `MAX_EXECUTION_REPAIRS=1` 允许表达 Agent 根据具体校验错误自动重生成一次；正常输出仍保持每轮一次模型调用。

## SDK compatibility

项目在模型配置初始化时检查 OpenAI SDK 的 `InputTokensDetails`。当当前
Agents SDK 的 LiteLLM adapter 未提供必填的 `cache_write_tokens` 时，缺失值
按 `0` 处理；SDK 后续原生兼容该字段后，此兼容逻辑自动不生效。
